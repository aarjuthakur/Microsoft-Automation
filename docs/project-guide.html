ms-forms-automation

What it does

This is the main project. It takes a CSV file describing a form (questions, types, options, validations, branching rules) and builds a real Microsoft Form by automating the browser. It can also test the form it just built — filling in every field and submitting.

CSV file → Parse & validate → Open MS Forms in Edge → Add questions one by one → Set restrictions & branching → Test by filling & submitting

File structure

ms-forms-automation/ builder/ FormEditorPage.ts ← builds the form in MS Forms editor BranchConfigurator.ts ← sets up branching rules between sections csv/ csvParser.ts ← reads CSV into FormField objects csvValidator.ts ← validates CSV structure and field types branchResolver.ts ← parses branching rules from CSV tester/ FormResponsePage.ts ← fills and submits form responses fixtures/ formFixture.ts ← Playwright fixtures (editorPage, responsePage, template) browserSetup.ts ← persistent Edge browser context tests/ buildOnly.spec.ts ← builds a form from CSV (no testing) testExisting.spec.ts ← tests an already-built form e2e/ happyPath.spec.ts ← full build + fill + submit functional/ inputTypes.spec.ts ← per-field-type testing smoke/ formLoads.spec.ts ← verify MS Forms loads formLoadPerf.spec.ts ← measure load time samples/ customer_feedback.csv ← example CSV templates debug_branching.csv multipage_survey.csv simple_text.csv workshop_entry.csv medical_checkup.csv docs/ project-presentation.html Presentation_Script_and_QA.docx server.ts ← web UI for CSV upload playwright.config.ts ← test runner config package.json tsconfig.json

CSV template format

Every form starts as a CSV file. Each row is one question. The columns tell the automation what kind of question to create and how to configure it.

ColumnPurposeExample
titleForm title (only the first row's value is used)Customer Feedback Survey
labelQuestion text shown to the respondentWhat is your name?
typeQuestion typetext, choice, rating, date, ranking, likert, nps, file_upload, section
requiredWhether the field must be filledtrue / false
optionsSemicolon-separated list of options (for choice, ranking, likert)Good;Average;Poor
restriction_typeValidation rule typeLength, Number, Min count, Max count
restriction_valueThe constraint value(s)10 (max length), 1-100 (range)
branch_conditionBranching: which option triggers a jumpPoor
branch_targetWhich section to jump toSection 3

The type column supports these question types:

  • text — Short or long text answer
  • choice — Radio buttons (single select) or checkboxes (if multiple allowed)
  • rating — Star rating (1-5 or 1-10)
  • date — Date picker
  • ranking — Drag-to-rank a list of items
  • likert — Matrix/grid of rating scales
  • nps — Net Promoter Score (0-10 scale)
  • file_upload — File attachment
  • section — Section divider (starts a new page in the form)

How the logic flows

Here's the full pipeline from CSV to a working, tested form:

Step 1: Parse the CSV

csvParser.ts parser

Reads the CSV file using the csv-parse library. Each row becomes a FormField object with properties like label, type, options, required, etc. The first row's title column becomes the form title.

Step 2: Validate

csvValidator.ts validator

Checks that every field has a valid type, that choice/ranking fields have options, that restriction types are recognized, and that branch targets reference existing sections. Catches errors before the browser even opens.

Step 3: Resolve branching

branchResolver.ts branching

Scans all fields for branch_condition and branch_target. Builds a map of branching rules: "if the user picks option X on question Y, jump to section Z". These rules get applied after all questions are created.

Step 4: Build the form

FormEditorPage.ts builder

This is the largest and most complex file. It drives the MS Forms editor using Playwright.

For each field in the parsed CSV, it:

  1. Clicks "Add new question" and selects the right type from the dropdown
  2. Types the question label
  3. Adds options if it's a choice/ranking/likert question
  4. Sets it as required if required: true
  5. Configures restrictions (length limits, number ranges, etc.)

Sections are added as dividers that create new pages in the form.

The form title is set via an API PATCH call (not by typing into the page) because the title field is not a regular contenteditable element.

Step 5: Configure branching

BranchConfigurator.ts branching

After all questions are built, this file opens the branching panel and configures each rule. For each branch rule, it clicks on the question, opens the branch settings, finds the option that matches the condition, and sets the "Go to" dropdown to the target section.

Step 6: Test the form

FormResponsePage.ts tester

Opens the form's response URL (the public-facing form) and fills every question. It works page by page: scans all visible questions on the current page, fills each one, then clicks "Next" until it reaches the "Submit" button. After submitting, it verifies the confirmation message appears.

Form builder internals

FormEditorPage.ts is the heart of the project. Here are the key pieces:

Question type adders

Each question type has its own method: addTextQuestion(), addChoiceQuestion(), addRatingQuestion(), addDateQuestion(), addRankingQuestion(), addLikertQuestion(), addNpsQuestion(), addFileUploadQuestion(), and addSection(). They all follow the same pattern: click "Add new" → select type → enter label → configure type-specific settings.

Title via API

MS Forms' title is not a regular text input — it's rendered by a React component that doesn't respond to normal typing. Instead, the builder captures the authentication headers from the browser's network requests, then sends an HTTP PATCH to the Forms API to set the title directly.

Restrictions

For questions with validation rules (like "max 100 characters" or "number between 1 and 10"), the builder opens the question's menu (…), clicks "Restrictions", selects the restriction type from a dropdown, and fills in the value.

Selector strategy

MS Forms uses data-automation-id attributes on many elements, which are stable across updates. The builder prefers these over CSS classes. Key selectors:

  • [data-automation-id="addQuestionButton"] — "Add new question" button
  • [data-automation-id="questionItem"] — a question container
  • [data-automation-id="textInput"] — text input field in response form

Form tester internals

FormResponsePage.ts fills forms using a page-scanning approach rather than iterating CSV fields. This is important because form labels on the page might not exactly match the CSV label text.

Page-by-page scanning

The tester works through the form one page at a time:

  1. Find all visible question containers on the current page
  2. For each container, try to match it to a CSV field by label text
  3. If matched, use the CSV field's test data. If not, detect the input type and fill generically
  4. Click "Next" to advance to the next page
  5. Repeat until the "Submit" button appears

Generic field detection

When a question doesn't match any CSV field, the tester detects the input type by checking what DOM elements exist in the container:

  • Has [data-automation-id="textInput"]? → Fill with "Test response"
  • Has [role="radio"][aria-label*="Star"]? → Click the 4th star
  • Has input[type="radio"]? → Click the first radio button
  • Has input[type="checkbox"]? → Check the first checkbox
  • Has a combobox? → Open dropdown and select first option

Rating stars

Rating fields are tricky. Stars are rendered as <span role="radio" aria-label="4 Star"> with SVG inside. The tester uses click({ force: true }) because the SVG overlay can intercept normal clicks.

Web server

server.ts entry point

A simple HTTP server that provides a web UI for uploading CSV files. Upload a CSV through the browser, and it kicks off the full pipeline (parse → validate → build → optionally test). The server shows real-time status updates while the form is being built.

Routes:

  • GET / — Upload page (HTML form)
  • POST /upload — Start building a form from the uploaded CSV
  • GET /status/:jobId — Poll for build progress

Tests

All tests use Playwright with a persistent Edge browser context (so the MS Forms login session is reused).

smoke/formLoads.spec.ts smoke

Verifies that MS Forms loads and the user is logged in. The most basic health check.

buildOnly.spec.ts build

Builds a form from a CSV without testing it. Set CSV_FILE env var to specify which template.

CSV_FILE=samples/customer_feedback.csv npx playwright test tests/buildOnly.spec.ts

testExisting.spec.ts test

Tests a form that already exists. Set RESPONSE_URL to the form's public URL. Fills every field and submits.

RESPONSE_URL=https://forms.cloud.microsoft/... npx playwright test tests/testExisting.spec.ts

e2e/happyPath.spec.ts e2e

The full pipeline: builds a form from CSV, then fills and submits it. Proves the entire system works end to end.

functional/inputTypes.spec.ts functional

Tests each field type individually on an existing form. Verifies that text, choice, rating, date, etc. can all be filled correctly.

How to run

First-time setup:

$cd ms-forms-automation
npm install
npx playwright install

First run — log into MS Forms: The first time you run anything, a browser window opens and you'll need to log into your Microsoft account. After that, the session is saved in a persistent browser profile and reused automatically.

Build a form from CSV:

$CSV_FILE=samples/customer_feedback.csv npx playwright test tests/buildOnly.spec.ts

Test an existing form:

$RESPONSE_URL=https://forms.cloud.microsoft/... npx playwright test tests/testExisting.spec.ts

Full end-to-end (build + test):

$CSV_FILE=samples/customer_feedback.csv npx playwright test tests/e2e/happyPath.spec.ts

Web UI (upload CSV through browser):

$npx tsx server.ts

Then open http://localhost:3000 in your browser.

Run all tests:

$npx playwright test

import-button-automation

What it does

This project automates the "Quick Import" feature in MS Forms. Instead of defining forms via CSV, you give it a Word document or PDF that contains survey questions, and MS Forms' AI converts it into a live form automatically. This automation handles all the UI clicks needed to make that happen.

Word/PDF file → Click Quick Import → Upload file → Select "Form" type → Wait for AI conversion → Click "Start review" → Form editor opens in new tab

File structure

import-button-automation/ src/ config.ts ← URLs, selectors, timeouts importForm.ts ← main entry point tests/ quickImport.spec.ts ← Playwright test for the import flow samples/ employee_satisfaction_survey.docx ← sample Word file employee_satisfaction_survey.pdf ← sample PDF file create-sample-docs.py ← generates the sample files playwright.config.ts package.json tsconfig.json

File details

src/config.ts config

Central configuration. Defines the MS Forms URL, path to the persistent browser profile (so login is remembered), all CSS selectors used, and timeout values.

src/importForm.ts entry

The main script. Contains 4 functions called in sequence: navigateToForms(), uploadViaQuickImport(), selectFormType(), and waitForConversionAndStartReview(). Browser stays open after completion so you can review the result.

create-sample-docs.py generator

Python script that generates a 7-question "Employee Satisfaction Survey" in both PDF and DOCX formats. Questions are structured so MS Forms' AI can parse them: numbered, with bullet-point options for multiple-choice questions and blank lines for text fields.

tests/quickImport.spec.ts test

Two tests: a smoke test that the Quick Import button exists, and an end-to-end test that imports a file and verifies the editor opens. The e2e test requires the IMPORT_FILE environment variable.

How the logic flows

The importForm.ts script has 4 main functions that run in sequence:

1. navigateToForms(page)

Opens https://forms.cloud.microsoft/Pages/DesignPagev2.aspx in the persistent Edge browser. Uses domcontentloaded instead of networkidle because MS Forms has background telemetry requests that never stop, causing networkidle to always time out. Handles login redirects if the session expired.

2. uploadViaQuickImport(page, filePath)

Gets the file into MS Forms using a multi-strategy approach:

  1. Strategy 1: Click the Quick Import button, listen for a filechooser event. (Doesn't work — the button opens a popover, not a file dialog.)
  2. Strategy 2: Inside the popover, find and click "Upload from this device". This triggers the file dialog. Upload through the filechooser event. This is the path that works.
  3. Strategy 3: Fall back to finding a hidden <input type="file"> and setting files on it directly.
  4. Strategy 4: Take a screenshot for debugging and throw an error.

3. selectFormType(page)

After the file uploads, MS Forms shows a dialog: "Import my file as" with two cards — "Form" and "Quiz". This function clicks the "Form" card (identified by its text "Collect quick survey or form responses").

4. waitForConversionAndStartReview(page)

MS Forms' AI now converts the document. A progress dialog shows "Converting [filename] to Microsoft Forms... 1 minute left to finish conversion". This function waits up to 2 minutes for the "Start review" button to appear.

Key detail: "Start review" opens the form editor in a new browser tab. The original tab stays on the MS Forms homepage. The script captures the new tab using context.waitForEvent('page') and reads the editor URL and form ID from it.

The four-step dialog sequence

This is the sequence of dialogs that appear after clicking Quick Import. Understanding this is key to understanding why the automation needed all four functions:

Dialog 1: Quick Import popover

Shows "Upload from this device" and a file size limit notice. Clicking "Upload from this device" opens the native file chooser.

Dialog 2: "Import my file as"

Two cards: Form ("Collect quick survey or form responses") and Quiz ("Enable automatic grading for easy assessment"). The automation clicks Form.

Dialog 3: Conversion progress

Shows a Word icon → Forms icon animation, "Converting [file] to Microsoft Forms...", and a time estimate. Has a Cancel button. Takes 10-30 seconds typically.

Dialog 4: Conversion complete

Shows "Your form has been converted successfully" with two buttons: "Import another" and "Start review". Clicking "Start review" opens the form editor in a new tab.

How to run

First-time setup:

$cd import-button-automation
npm install
npx playwright install

Import a Word document:

$npx tsx src/importForm.ts samples/employee_satisfaction_survey.docx

Import a PDF:

Shared concepts

Persistent browser profile

Both projects use Playwright's launchPersistentContext() with a profile directory stored in %LOCALAPPDATA%/ms_forms_automation/browser_profile. This means:

  • You log into Microsoft once on the first run
  • Every subsequent run reuses that session automatically
  • If the session expires, the scripts detect the login redirect and wait for you to log in again

Why Edge, not Chrome?

MS Forms works best in Microsoft Edge (it's a Microsoft product). Both projects launch Edge specifically with channel: 'msedge'. The --disable-blink-features=AutomationControlled flag prevents MS Forms from detecting the browser is automated.

domcontentloaded vs networkidle

MS Forms has persistent background network requests (telemetry, WebSocket connections) that never stop. Using Playwright's networkidle wait strategy causes timeouts because the page never becomes "idle". Both projects use domcontentloaded and then wait for specific UI elements to appear instead.

Selector fragility

MS Forms is a React application. CSS class names (like css-369) change between deployments. The automation relies on more stable selectors:

  • data-automation-id attributes (most reliable)
  • aria-label values (fairly stable)
  • role attributes (stable)
  • Text content matching (last resort)

If MS Forms updates their UI, the data-automation-id selectors are the least likely to break.
