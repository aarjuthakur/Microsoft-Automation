Capstone Project Presentation

MS Forms Automation

End-to-end automation of Microsoft Forms — from CSV template to live form creation, validation testing, and AI tool integration — built from scratch using Playwright and TypeScript.

TypeScript Playwright Microsoft Edge Page Object Model MCP Server Node.js
01 / Objective

Automating Microsoft Forms from Scratch

The goal of this project is to completely automate the creation and testing of Microsoft Forms using browser automation. Instead of manually clicking through the MS Forms editor to create forms one question at a time, this system:

  • Reads a CSV spreadsheet that defines the entire form structure (questions, types, options, validations, branching)
  • Opens a real Microsoft Edge browser with your logged-in Microsoft account
  • Creates the form automatically — adding questions, configuring restrictions, setting up branching between pages
  • Extracts the shareable response URL
  • Tests the created form by filling every field and submitting it
  • Exposes the entire pipeline as MCP tools so an AI assistant can trigger it
Why automate this? Creating complex forms with 20+ questions, input validations, and branching logic manually takes 30-60 minutes per form. This automation does it in under 3 minutes, with zero human error, and validates the form works correctly.
02 / Workflow

How the Project Was Built

The project was developed incrementally, solving one challenge at a time:

CSV Parser and Data Model

Designed the CSV format (8 columns: Page, Section, Type, Validation, Question, Required, Options, Branch). Built a parser that converts rows into typed TypeScript objects (FormField, FormTemplate, BranchPlan).

Browser Setup with Persistent Profile

Configured Playwright to launch Microsoft Edge with a persistent browser profile. This saves your login session so you don't have to log in to Microsoft every time the automation runs.

Form Builder (Page Object Model)

Built FormEditorPage — the core automation engine. Handles clicking "New Form", adding each question type, typing labels, filling options, toggling Required, and navigating the MS Forms editor.

Restriction and Validation System

Added automatic field validation: email fields get min 5 chars, phone fields get max 10 chars, name fields get min 3 chars. Also supports custom restrictions from the CSV. Uses regex patterns to validate CSV data quality.

Multi-Page Sections and Branching

Built BranchConfigurator to handle conditional navigation between pages. Supports expressions like rating >= 4 to route users to different sections based on their answers.

Title Setting via API Interception

The MS Forms editor has no editable title field. Solved this by intercepting the page's own API requests to capture authentication headers, then sending a PATCH request to the MS Forms OData API.

Test Suite with Playwright Assertions

Built a complete test framework: smoke tests, functional tests per input type, end-to-end tests, and performance tests. Each test uses real Playwright assertions (expect) to verify form behavior.

Web UI and MCP Server

Added a drag-and-drop web interface for CSV upload, and an MCP server that exposes the automation as AI-callable tools.

04 / Playwright Concepts

What I Learned and Used

Every concept below was learned and applied hands-on in this project. Here is what each means and exactly where it is used:

Async / Await Every file

What it means: JavaScript is single-threaded. When you do something that takes time (clicking a button, waiting for a page to load, making an API call), the code needs to wait without blocking everything else. async marks a function that contains asynchronous operations. await pauses execution until the operation completes.

Where I used it: Every Playwright interaction is async. For example, await page.goto(url) waits for the page to load, await input.fill('text') waits for the text to be typed, await expect(element).toBeVisible() waits for an element to appear.

async addTextQuestion(field: FormField): Promise<void> {
  await this.openQuestionPalette();      // wait for palette to open
  await this.clickQuestionType('Text');  // wait for click
  await this.typeQuestionTitle(field);   // wait for typing
  await this.toggleRequired(field);      // wait for toggle
}
Page Object Model (POM) builder/ and tester/

What it means: A design pattern where each web page gets its own class. The class has methods for every action you can take on that page. Tests call these methods instead of directly interacting with elements. This separates "what to do" from "how to do it."

Where I used it: FormEditorPage is the Page Object for the MS Forms editor. FormResponsePage is the Page Object for the response page. When MS Forms changes its UI, I update the Page Object — tests stay the same.

// Page Object encapsulates all editor interactions
class FormEditorPage {
  constructor(private page: Page) {}

  async createNewForm(title: string) { ... }
  async addTextQuestion(field: FormField) { ... }
  async getResponseUrl(): Promise<string> { ... }
}

// Test uses the Page Object — clean and readable
test('create form', async ({ editorPage }) => {
  await editorPage.createNewForm('My Form');
  await editorPage.addTextQuestion(nameField);
});
Fixtures fixtures/formFixture.ts

What it means: Fixtures are Playwright's way of sharing setup and teardown code across tests. Instead of repeating browser launch, page creation, and CSV parsing in every test, you define it once in a fixture. Each test declares which fixtures it needs, and Playwright provides them.

Where I used it: Custom fixtures for persistentContext (Edge with login), editorPage (FormEditorPage instance), responsePage (FormResponsePage instance), template (parsed CSV), and steps (step tracker).

export const test = base.extend<FormFixtures>({
  persistentContext: async ({}, use) => {
    const { context } = await launchPersistentEdge();
    await use(context);          // provide to tests
    await context.close();       // cleanup after tests
  },
  editorPage: async ({ persistentContext }, use) => {
    const page = persistentContext.pages()[0];
    await use(new FormEditorPage(page));
  },
});
Explicit Waits FormEditorPage.ts, FormResponsePage.ts

What it means: Telling Playwright to wait for a specific condition — an element becomes visible, a URL changes, text appears. Unlike implicit waits (a fixed sleep), explicit waits are condition-based and finish as soon as the condition is met.

Where I used it: waitFor({ state: 'visible' }) on form fields before interacting. waitForURL() after login redirects. waitForLoadState('networkidle') after navigation.

// Explicit wait: finishes as soon as the input appears
await input.waitFor({ state: 'visible', timeout: 15000 });

// Explicit wait: wait for login redirect to complete
await page.waitForURL('**/forms.cloud.microsoft/**');

// vs. Implicit wait: always waits full duration (avoid this)
await page.waitForTimeout(5000);  // sleeps 5s even if ready
Assertions with expect() tester/FormResponsePage.ts

What it means: Playwright's expect() is an auto-retrying assertion. When you write expect(element).toBeVisible(), it doesn't just check once — it keeps retrying until the element is visible or the timeout expires. This handles dynamic pages where elements appear asynchronously.

Where I used it: Every field test verifies its input was accepted: toHaveValue() for text fields, toBeChecked() for radio/checkbox, toBeVisible() for elements.

// Auto-retrying: keeps checking until value matches or timeout
await expect(input).toHaveValue('test@example.com');

// With custom error message for clear test reports
await expect(heading, 'Form heading should be visible').toBeVisible();

// Verifying interaction succeeded
await radios.first().click({ force: true });
await expect(radios.first()).toBeChecked();
Selectors and Locators builder/selectors.ts, tester/selectors.ts

What it means: Locators are how Playwright finds elements on the page. You can use CSS selectors ([data-automation-id="questionItem"]), role-based selectors (getByRole('button')), text selectors (getByText('Submit')), or XPath. Centralized selector files make maintenance easier.

Where I used it: Two selector files — one for the editor page, one for the response page. All selectors are defined as constants and used throughout the Page Objects.

// Centralized selectors — update here when MS Forms changes
export const RESPONSE = {
  questionContainer: '[data-automation-id="questionItem"]',
  textInput: '[data-automation-id="textInput"]',
  submitButton: 'button[data-automation-id="submitButton"]',
  nextButton: 'button[data-automation-id="nextButton"]',
};

// Used in Page Object
findQuestionContainer(label: string): Locator {
  return this.page.locator(RESPONSE.questionContainer, { hasText: label });
}
Persistent Browser Context fixtures/browserSetup.ts

What it means: Playwright can launch a browser with a saved user profile directory. This preserves cookies, login sessions, and browser state between runs. Essential for MS Forms because it requires Microsoft authentication.

Where I used it: launchPersistentEdge() opens Edge with a profile stored at %LOCALAPPDATA%\ms_forms_automation\browser_profile. Once you log in the first time, all subsequent runs reuse that session.

const context = await chromium.launchPersistentContext(
  BROWSER_PROFILE_DIR,
  {
    channel: 'msedge',
    headless: false,
    viewport: { width: 1280, height: 800 },
  }
);
Request Interception builder/FormEditorPage.ts

What it means: Playwright lets you listen to every network request the page makes with page.on('request'). You can read request URLs, headers, and bodies. This is powerful for capturing authentication tokens the page's own JavaScript sends.

Where I used it: To capture the anti-forgery token for the title API. The MS Forms page makes API calls that include auth headers. We intercept those requests, extract the headers, then reuse them in our own PATCH request.

page.on('request', (request) => {
  if (request.url().includes('/formapi/api/')) {
    capturedHeaders = request.headers();  // grab auth tokens
    apiBaseUrl = extractBaseUrl(request.url());
  }
});
await page.reload();  // triggers API calls we can intercept

Performance Testing tests/performance/

What it means: Measuring how fast the application responds. Page load time, interaction responsiveness, and resource usage are all performance metrics. Performance tests set thresholds and fail if the app is too slow.

Where I used it: A performance test that loads the form multiple times, measures each load, and asserts all loads are under 10 seconds. Also times individual field interactions to verify they respond within 500ms.

const start = Date.now();
await page.goto(responseUrl, { waitUntil: 'networkidle' });

expect(loadTime, 'Page should load within 10s').toBeLessThan(10000);
console.log(`Load time: ${loadTime}ms`);
05 / MCP Server

AI Tool Integration

What is MCP?

MCP (Model Context Protocol) is a standard created by Anthropic for connecting AI assistants to external tools and data. Think of it as a USB port for AI — a standard interface so any AI assistant can use any tool, without custom integration code for each combination.

Three Core Concepts

Tools

Functions the AI can call. Each has a name, description, and JSON Schema defining its inputs. Example: create_form accepts a CSV path and builds a form.

Resources

Read-only data the AI can access. Example: forms://templates returns the list of available CSV templates without modifying anything.

Transport

How AI communicates with the server. We use StdioServerTransport — JSON-RPC messages over standard input/output (stdin/stdout).

How It Works

Claude Code reads .mcp.json

The config file tells Claude Code how to start the MCP server: npx tsx mcp/formTestServer.ts

Server starts and registers tools

formTestServer.ts creates the MCP server, registers all 6 tools from tools.ts, and starts listening via stdin/stdout.

AI discovers available tools

Claude sends a tools/list JSON-RPC request. The server responds with all tool names, descriptions, and input schemas.

AI calls a tool

Claude sends tools/call with the tool name and arguments. The handler in handlers.ts executes the action (runs Playwright, reads files, etc.) and returns the result.

Architecture (3 Files)

mcp/tools.ts

Definitions. JSON Schema for each tool — name, description, required inputs. This is what the AI reads to know what it can do.

mcp/handlers.ts

Implementations. The actual code that runs when a tool is called. Wraps existing project functions — no duplicate logic.

mcp/formTestServer.ts

Server. Creates the MCP server with @modelcontextprotocol/sdk, registers tools and resources, starts StdioServerTransport.
